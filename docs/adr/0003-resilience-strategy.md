# ADR 0003: Resilience Strategy

- **Status:** Accepted
- **Date:** 2026-11-24
- **Course day:** Day 2

## Context

AirBreda shows the municipality whether traffic at the A27 Breda interchange drives NO₂ exceedances, and predicts the next hour. It is an **informational research dashboard**, not a safety system: nobody is evacuated based on it, and the official air-quality figures stay on luchtmeetnet.nl. The data it shows is already 30–90 minutes old when it is published.

The architecture (ADR-0001, ADR-0002) is **one EC2 VM** in eu-central-1 (Frankfurt) running Postgres, Redis, both ingesters and, from Day 4, the API/dashboard as Docker containers, plus an S3 bucket for raw NDW files.

Two facts set the ceiling on reliability:

- **AWS promises 99.5% uptime for a single EC2 instance** (instance-level SLA; credits apply below that). Multi-AZ deployments get 99.99%. A single-VM system cannot honestly promise more than its own VM is promised, and our own failures (bad deploys, a full disk, a crashed container) come on top.
- **The data can be rebuilt.** Luchtmeetnet serves years of history through the same API we already call. Every NDW snapshot is in S3 hourly. What can't be rebuilt from the sources is limited to our own derived state (flags), and that can be regenerated by re-running the ingestion code.

The December 2021 us-east-1 outage shows that a whole region can go down for hours. Protecting against that needs a second region, which is far beyond what this product needs.

## SLO for `GET /site/{id}`

| | |
|---|---|
| **SLI** | Share of `GET /site/{id}` requests that return HTTP 2xx within 1 second, measured at the server, per calendar month |
| **SLO** | **99%** |
| **Error budget** | 1% of a 30-day month = **7.2 hours/month** (~87.6 hours/year) |

**Why 99% and not 99.5% or 99.9%:**
- 99.9% (43 minutes/month) is impossible on one VM whose own SLA is 99.5%.
- 99.5% (3.6 hours/month) would let AWS alone use up the whole budget, leaving nothing for our own mistakes or for a restore (see RTO below).
- 99% matches what users need. A dashboard of hourly, already-delayed data that is down for an hour misses about one reading. Users lose nothing they can't see an hour later.

The budget is used deliberately: if a month's budget is intact, deploying during the day is fine. If it's spent, changes wait until the system is stable again.

## Disaster-recovery tier

| Tier | What it means for AirBreda | RTO | RPO | Extra cost / month* |
|---|---|---|---|---|
| **Backup & Restore** ← chosen | Nightly `pg_dump` to S3, raw NDW files already in S3, the whole system as code (`docker-compose.yml`, setup script). On failure: launch a new VM, `docker compose up`, restore the dump, backfill from the sources. | ~1 hour | ≤ 1 hour effective (see below) | ~$0 (S3 backups: cents) |
| Pilot Light | A small always-on standby (e.g. t3.micro in another AZ) running a Postgres replica; app containers started only on failover | ~15–30 min | minutes | ~+$11 (t3.micro ≈ $8.76 + disk + IP) |
| Warm Standby | A second, full copy of the stack running in another AZ, ready to take over | ~5–15 min | minutes | ~+$23 (≈ doubles: t3.small $17.52 + 20 GB disk ≈ $2 + public IPv4 $3.65) |
| Active-Active | Two or more VMs behind a load balancer with a replicated database | ~0 | ~0 | ~+$45 and up (second stack + load balancer), plus database replication work |

\*On-demand, eu-central-1, Nov 2026; baseline single VM ≈ $23/month (t3.small $0.024/h ≈ $17.52 + ~20 GB gp3 disk ≈ $2 + public IPv4 $0.005/h ≈ $3.65).

**Decision: Backup & Restore.**

- **RTO ~1 hour fits the error budget.** One full restore uses about 1 of the 7.2 hours a month.
- **Effective RPO is about 1 hour, even though the database backup is nightly.** After a restore, the air ingester re-fetches the last 50 hours on its first cycle (more if we backfill), and the traffic history is rebuilt from the S3 CSVs, which are at most an hour old. The only thing truly lost is anything in the Redis queue, and nothing depends on it yet (ADR-0002).
- **The next tier up, Pilot Light, costs ~$11/month more (about +45%)** to shorten recovery from ~1 hour to ~15–30 minutes, for a dashboard where an hour's outage hides one hourly reading. Warm Standby, which the course material suggests, roughly doubles the bill (~+$23/month) for the same benefit. Neither is worth it at this stage.

**What would change this:** the dashboard becoming a public alert channel (e.g. warning residents about exceedances), an SLA promised to the municipality, or a dependency on data that can't be re-fetched. The first step would then be Pilot Light in a second AZ, not multi-region.

## Resilience already built in

- **Retries with back-off** on every external call (3 attempts); a failed cycle is logged and the next cycle retries. One bad cycle never crashes a service (`run_forever` catches it).
- **Self-healing data:** each air cycle re-reads 50 hours, so an outage of our side up to ~2 days fills itself in. Idempotent upserts make re-runs harmless.
- **Containers restart themselves** (`restart: unless-stopped`), start in dependency order (Postgres and Redis must be healthy first), and shut down cleanly on `docker compose stop` (SIGTERM handled).
- **Observability:** structured JSON logs for every fetch, write, publish and data-quality event; `GET /health` per ingester (`ok` / `starting` / `stale` → HTTP 503 when there has been no successful fetch in ~2 poll intervals); one `ERROR BAD_DATA_THRESHOLD_EXCEEDED` when more than 10 bad readings arrive within an hour.

## Consequences

**Easier:** cheap (one VM), simple to reason about, and recovery is a script plus documented steps rather than replication infrastructure.

**Harder / to do:**
- **Backups must actually exist and be tested.** The nightly `pg_dump` → S3 job is planned for Day 3, together with a restore test. An untested backup doesn't count.
- **Never terminate the VM by accident:** its root disk (and with it the Postgres volume) is deleted on termination by default. Stopping it is safe.
- **Recovery is manual** and needs someone available. Acceptable for a research dashboard, not for a public service.
- **Single AZ, single region:** an AZ- or region-wide outage like December 2021 takes AirBreda down until AWS recovers or we rebuild elsewhere. That is accepted, and it costs at most a few hours of a 7.2-hour monthly budget in a typical month.
